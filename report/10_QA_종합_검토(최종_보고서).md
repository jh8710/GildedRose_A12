# Gilded Rose QA 최종 보고서

## 1. Executive Summary

Gilded Rose Java 프로젝트의 QA 활동은 요구사항 분석, 코드 품질 분석, 테스트 계획, 테스트 케이스 작성, 테스트 실행·결함 분석, Golden Master 자동화, 리팩토링 지원, 결함 관리 체계 수립까지 9단계로 진행되었다.

최종 검증 기준으로 `mvn test`를 실행한 결과, 단위 테스트 34개와 Golden Master 테스트 1개가 모두 통과했다.

| 항목 | 결과 | 판정 |
| --- | --- | --- |
| 자동화 테스트 | 35개 실행 / 35개 통과 | Pass |
| 테스트 통과율 | 100% | 목표 달성 |
| 요구사항 시나리오 커버 | 주요 시나리오 27개 기준 테스트 연결 | 목표 달성 |
| ItemType 커버 | Normal, Aged Brie, Backstage Pass, Sulfuras, Conjured 5종 | 목표 달성 |
| JaCoCo 라인 커버리지 | 미측정 (`jacoco-maven-plugin` 미설정) | 개선 필요 |
| JaCoCo 브랜치 커버리지 | 미측정 (`jacoco-maven-plugin` 미설정) | 개선 필요 |
| Open Critical/Major 결함 | 0건 | Pass |

현재 기능 검증 관점에서는 Green 상태이나, 커버리지 게이트는 아직 자동화되지 않았다. 다음 단계에서는 JaCoCo를 `pom.xml`에 추가해 라인/브랜치 커버리지 90% 이상을 CI 게이트로 고정하는 것이 우선이다.

### 2.2 요구사항 기반 완료율

[requirements_analysis.md](../docs/requirements_analysis.md)의 주요 테스트 시나리오 27개는 현재 `GildedRoseTest.java`의 파라미터화 테스트와 Golden Master 테스트로 연결되어 있다.

| 영역 | 요구사항/경계 | 테스트 반영 | 완료율 |
| --- | --- | --- | ---: |
| Normal | 기본 감소, 만료 후 2배 감소, `quality` 하한 | 7개 케이스 | 100% |
| Aged Brie | 증가, 만료 후 2배 증가, 상한 50 | 6개 케이스 | 100% |

| Conjured | 만료 전 -2, 만료 후 -4, 하한 0 | 7개 케이스 | 100% |
| Golden Master | 30일 출력 기준 회귀 | 1개 테스트 | 100% |

### 2.3 JaCoCo 목표 대비 현황

[test_plan.md](../docs/test_plan.md)의 커버리지 목표는 다음과 같다.

| 커버리지 항목 | 목표 | 현재 수치 | 판정 |
| --- | ---: | ---: | --- |
| 라인 커버리지 | 90% 이상 | 미측정 | JaCoCo 설정 필요 |
| 브랜치 커버리지 | 90% 이상 | 미측정 | JaCoCo 설정 필요 |
| 신규/수정 도메인 로직 | 95% 이상 | 미측정 | JaCoCo 설정 필요 |
| `GildedRose.updateQuality()` 주요 분기 | 100% 실행 목표 | 시나리오 기준 충족, 도구 수치 미측정 | 부분 충족 |

현재 `pom.xml`에는 `jacoco-maven-plugin`이 설정되어 있지 않고, `target/site/jacoco` 또는 `jacoco.xml` 산출물도 없다. 따라서 **테스트 완료율은 목표를 달성했지만, JaCoCo 수치 기반 커버리지 목표 달성 여부는 아직 판정할 수 없다.**

권장 조치:

1. `jacoco-maven-plugin`의 `prepare-agent`, `report`, `check` 실행을 `pom.xml`에 추가한다.
2. 1차 게이트는 라인 90%, 브랜치 85%로 시작한다.
3. Conjured 및 리팩토링 완료 후 라인/브랜치 90% 이상으로 상향한다.
4. 핵심 클래스인 `GildedRose`에 별도 기준을 두어 도메인 로직 누락을 방지한다.

### 3.1 현재 결함 상태

현재 테스트 실행 기준으로 재현 가능한 기능 결함은 없다.

| Severity | Open 결함 수 | 상태 |
| --- | ---: | --- |
| Critical | 0 | 없음 |
| Major | 0 | 없음 |
| Minor | 0 | 없음 |
| Info | 2 | 개선 항목으로 관리 |

Info로 남은 항목은 다음과 같다.

| 항목 | 설명 | 권장 조치 |
| --- | --- | --- |
| JaCoCo 미도입 | 목표 커버리지 수치를 자동 산출하지 못함 | `pom.xml` 플러그인 추가 |
| CI/Issue 자동 연동 미구현 | 결함 관리 워크플로우는 정의됐지만 자동화는 미적용 | GitHub Actions 및 Issue 템플릿 추가 |

### 3.2 아이템 타입별 결함 위험 패턴

| ItemType | 주요 결함 패턴 | 현재 보호 수단 | 잔여 위험 |
| --- | --- | --- | --- |
| Normal | 만료 후 2배 감소 누락, `sellIn=0` 처리 순서 오류 | P0/P1 경계 테스트 | 낮음 |
| Aged Brie | 상한 50 초과, 만료 후 증가량 누락 | `quality=49/50`, `sellIn=0/-1` 테스트 | 낮음 |
| Backstage Pass | 10일/5일/0일 전환점 오류, 콘서트 후 0 미처리 | 전환점 7개 테스트 + Golden Master | 중간 |
| Sulfuras | `sellIn` 감소, `quality=80` 예외 누락 | 불변성 테스트 | 낮음 |
| Conjured | 신규 요구사항 미구현, Normal 분기로 오분류 | -2/-4 및 하한 테스트 | 중간 |

Backstage Pass와 Conjured는 향후 변경 시 가장 먼저 회귀가 발생할 가능성이 높은 영역이다. Backstage Pass는 경계값이 많고, Conjured는 신규 요구사항이므로 이름 판별 규칙이 바뀌면 결함으로 이어질 수 있다.

| Major | 현재 없음 | 아이템 타입별 핵심 규칙 누락 |

## 4. 9단계 QA 활동 평가

| 단계 | 활동 | 효과 | 평가 |
| --- | --- | --- | --- |
| 1 | CursorRules 설계 | `Item` 클래스 수정 금지, 테스트 Green 후 리팩토링 원칙 고정 | 효과적 |
| 2 | 요구사항 분석 | 5개 ItemType과 27개 주요 시나리오 도출 | 매우 효과적 |
| 3 | 코드 품질 분석 | SRP/OCP 위반, Magic Number, 중복 로직 등 리팩토링 포인트 식별 | 효과적 |
| 4 | 테스트 계획 | P0/P1/P2 우선순위와 경계값 매트릭스 수립 | 매우 효과적 |
| 5 | 테스트 케이스 작성 | 34개 파라미터화 단위 테스트로 핵심 규칙 보호 | 매우 효과적 |
| 6 | 테스트 실행·결함 분석 | `mvn test` Green 및 결함 없음 확인 | 효과적 |
| 7 | Golden Master 자동화 | 30일 출력 기반 회귀 안전망 확보 | 매우 효과적 |
| 8 | 리팩토링 지원 | 안전한 구조 개선 로드맵 제공 | 효과적이나 일부 실행 필요 |
| 9 | 결함 관리 체계 | Severity × ItemType 분류와 보고 템플릿 수립 | 효과적이나 운영 자동화 필요 |

### 4.1 가장 효과적이었던 단계

1. **요구사항 분석**: 모호한 레거시 동작을 5개 ItemType과 27개 시나리오로 구조화해 테스트 설계의 기준이 됐다.
2. **테스트 계획 및 테스트 케이스 작성**: `quality=0/1/49/50`, `sellIn=0/-1`, Backstage 전환점이 빠짐없이 테스트로 고정됐다.
3. **Golden Master 자동화**: 단위 테스트가 놓칠 수 있는 30일 누적 출력 변화까지 감지할 수 있게 됐다.
4. **결함 관리 체계**: 결함을 Severity와 ItemType으로 분류해 향후 이슈 관리와 릴리스 게이트에 연결할 수 있는 기반을 마련했다.

### 4.2 개선이 필요한 단계

1. **커버리지 측정 단계**: JaCoCo 설정이 아직 없어 목표 대비 실제 라인/브랜치 커버리지 수치가 없다.
2. **CI 자동화 단계**: `mvn test`는 로컬에서 검증됐지만 PR 게이트로 자동 실행되는 GitHub Actions 구성은 없다.
3. **결함 워크플로우 운영 단계**: GitHub Issues 연동은 설계됐지만 템플릿과 라벨, 자동 등록은 아직 적용되지 않았다.
4. **리팩토링 실행 단계**: 현재 코드는 개선됐지만 `updateItem()`이 여전히 ItemType 분기를 알고 있어 OCP 관점의 잔여 부채가 있다.

## 5. 다음 레거시 프로젝트를 위한 Best Practice 5가지

1. **요구사항을 먼저 테스트 가능한 규칙으로 쪼갠다.**  
   레거시 코드는 코드가 문서 역할을 하는 경우가 많다. 먼저 ItemType, 경계값, 예외 규칙, 업데이트 순서를 표로 정리해야 테스트 누락을 줄일 수 있다.

2. **P0/P1/P2 우선순위를 두고 작은 테스트 안전망부터 만든다.**  
   모든 테스트를 한 번에 만들기보다 핵심 회귀(P0), 경계값(P1), 유지보수성(P2) 순서로 구성하면 빠르게 Green 기준선을 만들 수 있다.

3. **Golden Master를 단위 테스트의 보완재로 사용한다.**  
   단위 테스트는 규칙별 원인을 잘 잡고, Golden Master는 누적 출력 변화와 리팩토링 회귀를 잘 잡는다. 두 방식을 함께 쓰는 것이 레거시 안정화에 효과적이다.

4. **커버리지 숫자보다 요구사항 매핑을 먼저 확보하고, 이후 JaCoCo로 게이트화한다.**  
   라인 커버리지가 높아도 핵심 경계값이 빠질 수 있다. 요구사항 시나리오와 테스트를 먼저 연결한 뒤 라인/브랜치 90% 이상을 자동 검증해야 한다.

5. **결함 분류는 도메인 축과 심각도 축을 함께 사용한다.**  
   `Critical/Major/Minor/Info`만으로는 어느 규칙이 취약한지 보이지 않는다. ItemType과 함께 분류하면 Backstage, Conjured처럼 위험도가 높은 영역을 빠르게 찾을 수 있다.

### 6.1 정량 요약

| 항목 | 결과 |

| 작성된 QA 산출물 | 9개 단계 보고서 + 최종 보고서 |

| 자동화 테스트 | 35개 |
| 파라미터화 단위 테스트 데이터 | 34개 |
| Golden Master 회귀 테스트 | 1개 |
| 테스트 통과율 | 100% |
| Open Critical/Major 결함 | 0건 |
| 커버리지 자동 측정 | 미도입 |

시간 효과는 산출물 기준으로 보수적으로 평가하면 다음과 같다.

| 활동 | 수작업 예상 | Cursor AI 활용 후 | 추정 단축 효과 |
| --- | ---: | ---: | ---: |
| 요구사항·경계값 정리 | 1~2시간 | 수십 분 | 약 50~70% |
| 테스트 케이스 초안 작성 | 2~3시간 | 수십 분 | 약 60~75% |
| 결함 분류/보고 템플릿 작성 | 1시간 내외 | 수십 분 | 약 50~70% |
| 최종 보고서 초안화 | 1~2시간 | 수십 분 | 약 50~70% |

위 수치는 실제 조직별 프로세스에 따라 달라질 수 있으나, 이번 프로젝트에서는 반복적인 표 작성, 경계값 조합 도출, 결함 템플릿 구성, 보고서 구조화에서 시간 단축 효과가 컸다.

### 6.2 정성 요약

Cursor AI는 다음 영역에서 효과가 높았다.

1. **결함 조기 발견 관점**  
   Conjured가 Normal 분기로 처리될 수 있는 위험, Backstage Pass 전환점 오류, `sellIn=0/-1` 처리 순서 오류를 테스트 설계 단계에서 먼저 드러냈다.

2. **커버리지 향상 관점**  
   기존 단순 테스트에서 5개 ItemType 전체와 경계값을 포함한 34개 단위 테스트로 확대했다. 수치 커버리지는 아직 미측정이지만, 요구사항 기반 커버는 크게 향상됐다.

3. **문서 품질 관점**  
   요구사항, 테스트 계획, 결함 관리, 리팩토링 계획이 같은 용어와 구조를 공유하도록 정리되어 QA 산출물 간 추적성이 좋아졌다.

4. **리팩토링 안정성 관점**  
   테스트 Green 원칙, Golden Master, 결함 분류 체계를 먼저 세운 덕분에 구조 개선을 안전하게 진행할 수 있는 기준선이 마련됐다.

5. **협업 관점**  
   Severity × ItemType 매트릭스, GitHub Issues 워크플로우, PR 게이트 기준이 정의되어 개발자·QA·리뷰어가 같은 기준으로 결함을 판단할 수 있다.

## 8. 최종 결론

이번 QA 활동은 레거시 Gilded Rose 프로젝트를 요구사항 기반으로 재정렬하고, 핵심 도메인 규칙을 테스트로 보호하며, 결함 관리와 리팩토링 기준까지 수립했다는 점에서 성공적이다.

현재 기준으로 자동화 테스트는 35개 모두 통과하며, Open Critical/Major 결함은 없다. 다만 JaCoCo 기반 커버리지 수치가 아직 없으므로, “기능 테스트 Green” 상태와 “커버리지 게이트 완료” 상태를 구분해야 한다.

다음 단계의 핵심은 **JaCoCo + CI + Issue Workflow**를 연결해 현재의 QA 산출물을 운영 가능한 품질 게이트로 전환하는 것이다.
